## 코딩 에이전트 작업 규칙

1. 작업을 시작하기 전에 이 문서의 기능 범위, 체크리스트, 우선순위를 확인한다.
2. 체크리스트의 미적용 항목을 구현할 때 관련된 모든 라우트, 템플릿, Socket 이벤트 및 데이터베이스 구조를 함께 확인한다.
3. 보안 항목을 완료 처리하기 전에 아래의 완료 조건을 테스트로 검증한다.
4. 구현을 완료하면 체크박스와 코드 근거를 갱신하고, 버전별 상세 내역은 [SECURITY_CHANGELOG.md](SECURITY_CHANGELOG.md)에 기록한다.
5. 기능 또는 구조의 변경 규모에 따라 `Current Version`을 변경한다.
6. 데이터베이스 스키마를 변경하는 경우 기존 데이터에 대한 마이그레이션 또는 호환 방안을 함께 작성한다.
7. 비밀키, 비밀번호, 토큰 및 운영 설정값을 소스 코드나 Git에 추가하지 않는다.
8. 버전이 변경되면 테스트 통과 후 [VERSIONING.md](VERSIONING.md)의 절차에 따라 버전 커밋을 생성한다.

체크박스 표기 규칙:

- `[x]`: 적용 및 검증 완료
- `[ ]`: 미적용 또는 검증 미완료
- `N/A`: 현재 구현된 기능에는 적용 대상이 없음

## 버전 관리 정책

이 프로젝트는 `Major.Minor` 형식으로 버전을 관리한다.
버전별 상세 보안 조치는 [SECURITY_CHANGELOG.md](SECURITY_CHANGELOG.md), 커밋
절차와 점검 항목은 [VERSIONING.md](VERSIONING.md)를 따른다.

### Version 1.0

- 최초 작성 및 최초 기준 버전은 `1.0`으로 한다.
- 현재 코드와 이 보안 체크리스트의 기준 버전이다.

### Minor Version 증가

다음과 같은 기존 시스템의 개선 및 하위 기능 추가는 Minor Version을 증가시킨다.

- 보안 취약점 해결
- 기존 데이터베이스 구조의 소규모 개선
- 기존 페이지의 상세 기능 추가
- 신규 페이지 추가
- 입력 검증, 권한 확인, 감사 로그 등 기존 기능의 고도화
- 기존 기능과 호환되는 컬럼, 인덱스 또는 상태값 추가

예시:

- `1.0` → `1.1`: CSRF, 비밀번호 해시, 세션 보안 적용
- `1.1` → `1.2`: 상품 수정·삭제 페이지 및 소유자 검증 추가
- `2.0` → `2.1`: 송금 기능의 거래 내역 조회 또는 취소 정책 추가

### Major Version 증가

다음과 같이 서비스 구조나 핵심 도메인이 크게 확장되는 경우 Major Version을 증가시키고 Minor Version을 `0`으로 초기화한다.

- 새로운 핵심 데이터베이스 스키마 또는 주요 도메인 테이블 추가
- 송금 또는 결제 기능 추가
- 상품 검색 기능 추가
- 관리자 페이지 및 관리자 권한 체계 추가
- 기존 데이터 흐름이나 권한 구조를 크게 변경하는 기능 추가

예시:

- `1.x` → `2.0`: 송금 기능과 거래 테이블 추가
- `2.x` → `3.0`: 관리자 페이지와 역할 기반 권한 체계 추가

### 버전 결정 기준

| 변경 내용 | 버전 변경 |
|---|---|
| 최초 작성 | `1.0` |
| 보안 패치 및 기존 기능 개선 | Minor `+0.1` |
| 페이지 또는 상세 기능 추가 | Minor `+0.1` |
| 기존 스키마의 호환 가능한 소규모 변경 | Minor `+0.1` |
| 핵심 도메인·대형 기능·주요 스키마 추가 | Major `+1.0`, Minor는 `0` |
| Major 변경 이후의 소규모 개선 | 해당 Major의 Minor `+0.1` |

데이터베이스 변경이 버전 기준상 모호한 경우 다음 원칙을 적용한다.

- 기존 기능을 보완하는 컬럼, 인덱스, 제약조건 추가는 Minor 변경으로 본다.
- 새로운 핵심 업무 데이터를 저장하는 테이블 또는 서비스 흐름 추가는 Major 변경으로 본다.

- 구매마다 현재 비밀번호와 CSRF를 확인한다.
- 구매자 잔액 차감·판매자 입금·주문 생성을 하나의 트랜잭션으로 처리한다.

- 주문의 상품·사용자·가격·송금 요청을 DB Trigger에서 재검증한다.
- 주문 완료 원장의 UPDATE·DELETE를 차단한다.
- 관리자 계정의 구매와 주문 내역 접근을 차단한다.

## 공통 완료 조건

체크리스트 항목은 다음 조건을 모두 만족한 경우에만 `[x]`로 변경한다.

1. 서버 코드에 보안 조치가 구현되어 있다.
2. 브라우저 또는 클라이언트 검증만으로 처리하지 않는다.
3. 정상 요청과 악의적인 요청에 대한 테스트가 존재한다.
4. 실패 시 안전한 상태와 응답을 유지한다.
5. 관련 설정이 개발 환경과 운영 환경에서 구분되어 있다.
6. 비밀정보나 실제 사용자 데이터가 테스트 및 Git 이력에 새로 포함되지 않는다.
7. 코드 근거와 테스트 결과가 이 문서 또는 변경 이력에 기록되어 있다.

## 권장 검증 시나리오

- CSRF 토큰이 없거나 잘못된 모든 상태 변경 요청이 거부되는지 확인
- 짧거나 지나치게 긴 사용자명·비밀번호가 거부되는지 확인
- DB 유출 상황에서도 비밀번호 원문을 즉시 확인할 수 없는지 확인
- 음수, 문자, 지나치게 큰 가격이 거부되는지 확인
- 상품·프로필·신고 입력에 XSS 문자열을 넣어도 실행되지 않는지 확인
- 비로그인 Socket 연결과 메시지 전송이 거부되는지 확인
- 채팅의 사용자명을 클라이언트가 위조할 수 없는지 확인
- 1대1 메시지와 기록이 발신자·수신자 외 사용자에게 노출되지 않는지 확인
- 메시지 및 신고를 빠르게 반복하면 `429` 또는 이에 준하는 제한이 적용되는지 확인
- 비밀번호 변경 후 기존 HTTP·Socket 세션과 이전 비밀번호가 거부되는지 확인
- 존재하지 않는 사용자·상품을 대상으로 레코드를 생성할 수 없는지 확인
- 잔액보다 큰 송금과 같은 요청 ID의 반복 송금이 원장에 남지 않는지 확인
- 송금 대상 목록·POST·DB Trigger에서 일반 사용자끼리의 송금이 차단되고
  일반 사용자→사업자만 허용되는지 확인
- 송금 내역이 발신자 외 사용자에게 노출되지 않는지 확인
- 운영 설정에서 디버그 정보, Stack Trace 및 DB 오류가 응답에 노출되지 않는지 확인
- 세션 쿠키에 HttpOnly, Secure 및 명시한 SameSite 속성이 적용되는지 확인
- 사업자 부여·해제에서 CSRF·재인증·활성 상태·잔액 0원 조건과 세션 무효화를 우회할 수 없는지 확인
- 사업자가 송금 발신·구매 경로에 접근할 수 없고 일반 사용자의 송금과 상품
  판매 대금만 수취하는지 확인
- 일반 사용자·관리자 계정이 내 상품 관리·상품 등록·수정·일반 삭제 경로를 우회할 수 없는지 확인
- 관리자 전체 채팅은 차단하면서 관리자↔사업자·일반 사용자 1대1 채팅은 허용되는지 확인
- 같은 역할끼리의 1대1 채팅이 목록·HTTP·Socket·DB Trigger에서 차단되는지 확인
- 관리자 신고 접수함이 접수된 신고 내용을 표시하고 일반 사용자의 신고 접수 기능은 유지하는지 확인
- 사업자 신고 메뉴·GET·POST·DB INSERT와 자기 상품 신고가 차단되는지 확인
- 관리자 상품 관리 삭제가 CSRF·삭제 사유·현재 비밀번호를 요구하고 감사 이력을 남기는지 확인
- 회원가입이 기존 모든 사용자명과 중복되지 않고 신규 계정을 `is_admin=0`, `account_type='user'`로 생성하는지 확인
- 관리자·사업자 계정의 회원 탈퇴 메뉴와 직접 POST 요청이 차단되는지 확인
